# Plan：上下文感知任务澄清与可选 Agent 执行

> Source PRD：`docs/PRD-Context-Aware-Task-Clarification-and-Agent-Execution.md`
> UI contract：`docs/mockups/context-aware-task-clarification/README.md`
> Planning model：tracer-bullet vertical slices
> Readiness：`Ready with assumptions`

本计划采用“先智能完善任务，再按需交给 Agent”的切片。Phase 1-3 构成可独立上线的 MVP-1；Phase 4 以后只有在 MVP-1 验证有价值后再进入，不阻塞人工任务管理。

## Architectural Decisions

- **事实源**：任务、来源关系、任务简报、执行结果和验收仍以 Vault 内 Markdown 为事实源，不引入新数据库。
- **展示边界**：TaskNotes 继续拥有看板、日历、排期和人工状态；ATL 只在自己拥有的任务详情 Modal 中提供澄清与可选执行。
- **主完成条件**：任务简报保存成功即完成任务澄清；不要求 Agent、工作区或权限。
- **状态解耦**：任务简报状态、Agent 运行状态与 TaskNotes 看板状态分开。保存简报不移动看板；Agent 返回结果也不自动完成任务。
- **上下文边界**：只读取稳定引用、用户可见且可排除的授权来源；长内容有界处理并明确截断。
- **个人上下文**：`07_System/Agent_Context/` 是可选来源，为空不报错；长期记忆只能生成候选并由用户确认写入。
- **项目边界**：业务项目用于管理与复盘，Agent 工作区用于执行目录；MVP-1 不迁移现有项目字段。
- **模型边界**：任务澄清复用现有可配置 Model / Base URL；ATL 不保存 API Key。模型失败必须保留人工编辑能力。
- **Agent 边界**：Agent 只在用户主动展开并确认后启动；稳定人工交接始终是兜底。
- **安全与兼容**：不修改 TaskNotes 插件内部文件、钉钉镜像或同步助手来源；高风险动作继续单独确认。
- **工程规则**：Node 24、测试先行、临时 Vault fixture、状态变更经 service、Agent 不直接修改领域状态。

## Phase 1：单任务一键形成并保存简报

**User stories**：手动任务或已有 Inbox 任务信息充分时，用户希望 AI 直接把任务想清楚，然后自己在 TaskNotes 继续推进。

### What To Build

完成最窄的端到端路径：从一条已有任务打开 ATL 任务澄清 Modal，只使用任务标题、正文和现有项目说明生成目标、下一步和完成条件。用户可编辑并保存简报，随后返回原任务；整个过程不出现 Agent 配置，也不改变看板、排期或项目。

### Acceptance Criteria

- [ ] 已有任务可以从 ATL 命令或文件菜单打开新的任务澄清 Modal。
- [ ] 信息充分时无需对话即可得到可编辑的目标、下一步和完成条件。
- [ ] 用户保存后重新打开任务能看到同一版本的简报。
- [ ] 保存不会改变状态、`scheduled`、`due`、优先级或业务项目。
- [ ] 保存链路不会检测或启动 Agent Runtime。
- [ ] 模型不可用时仍能直接人工编辑并保存。
- [ ] 现有 TaskNotes 看板、日历和“移到待办”流程回归通过。

---

## Phase 2：可见、可排除、可追溯的多来源上下文

**User stories**：同步助手任务已有原消息，会议任务已有 AI 听记与附件，用户不想重复描述，也需要知道 AI 实际读取了什么。

### What To Build

在 Phase 1 完整链路上增加有界上下文发现。系统识别任务来源锚点、已授权附件、业务项目和适用个人上下文，先展示来源清单与解析状态，再生成简报。用户可以排除来源并重新生成，任务只保存引用和确认结果。

### Acceptance Criteria

- [ ] 同步助手、复盘、钉钉/会议和手动任务均能显示可识别的来源类型。
- [ ] 有稳定锚点时只读取相关段落，不发送整日同步助手内容。
- [ ] 仅解析用户允许的 `txt/md/docx/pdf`，未选择资料不进入模型输入。
- [ ] 长内容显示摘要、引用与“部分读取”状态，不伪装成完整扫描。
- [ ] 用户排除某来源后，发送范围和生成结果随之更新。
- [ ] `07_System/Agent_Context/` 不存在或为空时仍能完成 Phase 1 链路。
- [ ] 钉钉镜像、同步助手来源和附件原文件保持未修改。

---

## Phase 3：阻断性澄清、冲突处理与失败恢复

**User stories**：信息不足时用户只回答真正关键的问题；来源冲突时用户决定采用哪个依据；失败时不丢失已有工作。

### What To Build

让模型在生成前返回“充分、需要澄清、冲突”之一。需要澄清时只提出当前阻止下一步或完成条件成立的问题；冲突时并列展示来源，由用户选择。每次回答实时更新简报草稿，模型失败和并发修改都可恢复。

### Acceptance Criteria

- [ ] 任务信息充分时不出现无意义问答。
- [ ] 信息不足时每轮只围绕少量阻断性问题，不重复询问已有事实。
- [ ] 关键冲突显示双方内容与来源，未选择前不会静默合并。
- [ ] 用户回答、手工编辑与 AI 推断在简报中可区分。
- [ ] 模型超时、无效结构和来源失效均显示就地错误与恢复动作。
- [ ] 失败后任务原文、用户回答、已读取来源和草稿不丢失。
- [ ] 并发修改时停止覆盖并提示刷新或合并。
- [ ] Phase 1-2 的保存不改看板行为持续通过。

### MVP-1 Release Gate

- [ ] 在临时 Vault 完成单元、集成和 Modal 交互测试。
- [ ] 真实 Vault 冒烟只在显式写入开关下执行，并验证来源文件未变。
- [ ] 在 Obsidian 中验证信息充分、需要澄清、冲突、仅保存和模型失败五个状态。
- [ ] 用户可以连续用真实任务验证一周，而无需配置 Agent Runtime。

## Phase 4：可选 Agent 区与稳定人工交接

**User stories**：用户在简报完成后偶尔希望委托执行，但也可以稍后再决定；运行时不可用时仍能把完整上下文交给现有 Agent 工具。

### What To Build

在已保存简报下增加默认收起的“交给 Agent”区域。用户展开后才选择 Agent、工作区、执行方式与权限。首个完整切片只冻结执行包并支持可审阅、可复制的人工交接，不承诺自动建立原生会话。

### Acceptance Criteria

- [ ] Agent 区默认收起，未展开时不检测运行时、不要求工作区或权限。
- [ ] 业务项目和 Agent 工作区在界面与数据语义上分离。
- [ ] 用户可通过文件夹选择器登记工作区并看到有效性和 Git 状态摘要。
- [ ] 发送前展示任务简报、上下文范围、权限和禁止事项。
- [ ] 执行包冻结后，来源变化不会静默改变已确认输入。
- [ ] 人工交接可以复制可读执行包并打开目标工作区。
- [ ] 工作区失效或运行时不可用不会改变任务状态。

### Phase Prerequisite

- [ ] 完成现有业务项目字段、TaskNotes 项目字段和工作区注册表的双读单写迁移规格。

---

## Phase 5：Codex 会话、结果回写与人工验收

**User stories**：代码任务关联到本地 Codex 项目后，用户希望从 Obsidian 启动、打开或继续会话，并在任务中验收结果。

### What To Build

选择一条已验证的 Codex 本地执行路径完成首个真实 Agent vertical slice：建立会话关系、展示当前状态、回写最终摘要与产物、等待人工验收，并能在要求修改时继续原会话。无法取得稳定会话关系时自动降级到 Phase 4 人工交接。

### Acceptance Criteria

- [ ] 只有准入检查和会话关系都成功后才显示“运行中”。
- [ ] 用户能从任务打开或继续对应 Codex 会话。
- [ ] 运行状态来自真实事件，不使用伪百分比。
- [ ] 最终摘要、修改文件、Commit/PR 和报告以可读产物展示。
- [ ] Agent 返回结果后任务等待人工验收，不自动完成。
- [ ] 要求修改时优先继续原会话并保留历史结果。
- [ ] 无会话 ID、执行中断或工作区冲突均可恢复或降级人工交接。
- [ ] 提交、推送、PR、部署和外部发送分别保持人工确认。

### Phase Prerequisite

- [ ] 技术探针证明会话创建、恢复和用户可见性满足产品合同；否则本阶段不启动。

---

## Phase 6：Claude Code 会话能力对齐

**User stories**：用户希望在同一任务详情中选择 Claude Code，并获得与 Codex 一致的执行状态、结果和返工体验。

### What To Build

在不破坏现有受控 Claude 调研 Runner 的前提下，把 Phase 5 已验证的执行包、会话状态、结果回写和验收合同适配到 Claude Code。功能不可用时继续使用现有后台只读或人工交接路径。

### Acceptance Criteria

- [ ] Claude Code 与 Codex 使用同一用户可见执行包、权限和验收语义。
- [ ] 连续会话可恢复；不能恢复时明确标记为新会话而非伪装延续。
- [ ] 现有只读调研的工具、文件和网络权限没有被扩大。
- [ ] 失败、超时、停止和返工状态与 Codex 具有一致恢复入口。
- [ ] 现有 Claude 后台调研、Artifact、审计和人工验收回归通过。

---

## Phase 7：复盘回流与发布硬化

**User stories**：用户希望每日和每周复盘能说明任务如何从输入变成清晰行动与实际产物，而不是只统计 Agent 运行次数。

### What To Build

把任务澄清、人工推进、可选 Agent 会话、产物和验收事件汇总到每日 / 每周复盘。完成安全、兼容、性能和升级回滚验证，保持私密对话与敏感上下文不进入复盘正文。

### Acceptance Criteria

- [ ] 复盘区分新增任务、已完善、人工完成、已启动、待验收、返工和阻塞。
- [ ] 复盘关联来源、简报、产物和验收，但不复制完整私密对话。
- [ ] 人工决策与 Agent 贡献分别呈现，不把运行次数当作成果。
- [ ] 上下文装配在大型任务和长听记下不会阻塞 Obsidian 主线程。
- [ ] 升级、关闭功能和回滚不会破坏已有 Markdown 与 TaskNotes 视图。
- [ ] 全量测试、类型检查、lint、build、安全检查和双视口 UI 回归通过。

## Recommended Delivery Order

1. 先只批准 Phase 1，实现最小完整闭环。
2. Phase 1 真实使用后再进入 Phase 2-3，形成 MVP-1。
3. MVP-1 连续使用一周且确实产生“想清楚任务”的价值，再决定是否启动 Phase 4。
4. Phase 5、6 必须分别通过会话技术探针，不做双 Agent 同时大开发。
5. Phase 7 在实际事件数据出现后再接复盘，避免提前设计空指标。
